# Durable receiver operations

The exact historical replay is published separately. New P3 training waits for the advertised common READY, verifies the pinned hashes and fresh shared gates/smoke, and then launches the producer-owned foreground coordinator detached in its own process group. No model/trainer is defined in the receiver namespace.

Local controller: `RECEIVER_RUNTIME/control.py` (absolute location is in the receiver receipt supplied to the user). Commands are `status`, `pause`, `resume`, `retry --job EXACT_JOB_ID`, `stop` and `stop --active`. Pause stops new queue claims and allows active jobs to finish. Default stop first requests that same pause and stops the receiver; it leaves active workers alive. Explicit `stop --active` additionally terminates only the identified task coordinator process group. Resume starts a detached receiver if it is down. The lock prevents a second receiver from creating duplicate supervisors. A supervisor restart must reclaim only dead PID/start-time leases through the common runner, never a live process on a stale heartbeat alone.

The receiver polls with backoff capped at120 seconds and preserves the original 12-hour READY deadline across restarts. On timeout it stops polling and retains a precise blocked receipt; publication retries at most three times on that terminal path, preserving unsynced files if authentication/network access is unavailable. Normal publication is every5–10 minutes; a network outage does not signal GPU workers. All Git writes are on the RTX3090 result branch and its dedicated publication worktree.

Executing receiver versions and scientific worktrees are immutable. Scientific source revisions and gate failures belong to A5000; issues are published under this owner's result directory. The receiver itself handles Git/status/control/consolidation only. Source-specific resume, retry, rebatching and affected-job invalidation belong to the common runner and must be demonstrated before launch.

Cross-server consolidation reads immutable source result commits. It requires complete expected per-date support digests, row counts, protocol/input/split/mask/core-source hashes, selected configuration identity and all three seeds for the mean comparison. Incomplete comparisons remain explicit. Historical and new P3 training namespaces are kept separate. Consolidation runs periodically, including after local terminal jobs while the peer is still pending; finalization is dependency driven. Compact exported tables/calibration/subgroups are retained from each owner; primary paired/rolling tables are regenerated when complete compatible source exports arrive.

Before READY exists, the ownership expectation (30 new owned fits) is not an initialized scientific queue. Shared verify/smoke, per-job checkpoint validation and actual generated DAG counts are pending. No claim of launched training is made until a real task heartbeat/log/checkpoint exists.
